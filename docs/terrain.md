# Balance: terrain and maps

How terrain is defined, how a map is stored and how it is drawn. Milestone M1
built this; M3 added the rule for what can be walked on and the Orichalcum
rock.

## Terrain types

Each kind of ground is one small file in `data/terrain/` (a `TerrainType`
resource). It says:

| Field | Meaning |
| --- | --- |
| `id` | Internal name, e.g. `grass` |
| `display_name` | Name shown to the player |
| `symbol` | The one character that stands for it in a map |
| `walkable` | Can ground units cross it? |
| `buildable` | Can buildings stand on it? |
| `minimap_color` | Its colour on the minimap |
| `tiles` | Its tile image in `assets/tiles/` |

A **biome** (`data/biomes/`) lists the terrain types that belong together, in
drawing order. The first one is the ground that lies under everything.

| Biome | Terrain | Symbol | Walkable | Buildable |
| --- | --- | --- | --- | --- |
| Forest | Grass (ground) | `.` | yes | no |
| Forest | Dirt | `d` | yes | no |
| Forest | Stone | `s` | yes | **yes** |
| Forest | Water | `w` | **no** | no |
| Forest | Forest | `f` | **no** | no |
| Forest | Orichalcum rock | `o` | **no** | no |
| Desert | Sand (ground) | `.` | yes | no |
| Desert | Dunes | `u` | yes | no |
| Desert | Hardpan | `h` | yes | no |
| Desert | Rock | `r` | yes | **yes** |
| Desert | Orichalcum rock | `o` | **no** | no |

Buildings standing only on rock ground is a design decision.

What can be walked on is a design decision too (see "Rules of the battlefield"
in [design.md](design.md)): units walk on flat ground only. So trees and water
block movement, and so does the Orichalcum rock, which is a big rock
formation. "Stone" and "Rock" in the table are the flat rock ground that
buildings stand on, not big rocks, so they can be walked on.

## Maps

A map is a file in `data/maps/` (a `MapData` resource): a name, a biome, the
start positions of the two sides, the control point (the middle of the
Orichalcum rock) and the grid, written as one line of text per row and one
character per cell. For example, a tiny forest map with a pond:

```
....
.ww.
.w..
....
```

The two maps so far, `forest_01` and `desert_01`, are 64x48 cells. They are
generated by `tools/make_maps.py` but are plain text and can be edited by hand.
A cell is 32x32 pixels, so these maps are 2048x1536 pixels, a little under three
screens wide.

Both maps have the Orichalcum rock formation in the middle (about six cells
wide and four tall), in a clearing, with a track from the clearing to each
start position. The generator checks that both starts can walk to the rock and
to each other, and stops if they cannot. On the forest map a few pockets of
grass are walled in by trees or water and cannot be reached; nothing starts
there.

`MapData` answers the questions the game will ask: how big the map is, what
terrain a cell has, whether a cell can be walked on or built on. It also reports
problems (rows of different length, unknown symbols) instead of failing quietly.

## How the map is drawn

`TerrainView` (`scripts/ui/terrain_view.gd`) draws a map with one `TileMapLayer`
per terrain type, stacked in the biome's drawing order.

- **Ground** (grass or sand): one tile per cell. The ground texture is an 8x8
  block of tiles that repeats without visible seams.
- **Every other terrain** is drawn on top of the ground with **border tiles** on
  a grid shifted by half a cell. Each border tile sits on the corner where four
  cells meet, and which tile is used depends on which of those four cells have
  the terrain (15 possible shapes). This is why patches have rounded, irregular
  edges instead of square ones, without needing a hand-drawn tile for every
  pair of neighbouring terrains.
- **Props** (shrubs and lone trees on grass; dry tufts and stones on sand) are
  scattered on open ground only. Which cell gets which prop depends only on the
  cell's position, so a map always looks the same. They are decoration and do
  not affect play.

Details that make it look like the mockups:

- Borders wander by a few pixels and are gritty, not smooth.
- Neighbouring patches overlap slightly, so the ground rarely shows between
  them.
- Forest is made of whole tree tops: a tree belongs to the forest if its centre
  is inside, so no tree is cut in half at the edge.
- Stone and rock have a thin lit edge to the north-west and a dark edge to the
  south-east, so they read as a low step.
- Water has a narrow bank.
- Dune patches end in stripes.
- The Orichalcum rock is cracked rock studded with small ore crystals, with
  the same low lit and dark edges as stone, after the formation in the
  approved mockups. The crystals are densest where the tile texture starts
  (every eight cells), so a formation looks best with its middle on a grid
  corner whose cell coordinates are multiples of eight. The map centre is one.

## The tile images

`tools/make_tiles.py` generates all tile images in `assets/tiles/<biome>/`. Do
not edit them by hand; change the script and run it again.

| File | Size | Contents |
| --- | --- | --- |
| ground (`grass.png`, `sand.png`) | 256x256 | 8x8 tiles, opaque |
| other terrain (`dirt.png`, `ore_rock.png`, ...) | 2048x512 | 64 columns x 16 rows of border tiles, transparent background |
| `decor.png` | 256x32 | 8 props, transparent background |

In a border image the column is the tile's position within the repeating 8x8
block and the row is the shape: top-left cell 1 + top-right 2 + bottom-left 4 +
bottom-right 8. Row 0 is empty.

The palettes and the way textures are built (banded colour ramps, per-pixel
grit, small shaded elements lit from the north-west) come from the approved v4
mockup scripts in `mockups/src/`.

The shroud (see [units.md](units.md)) is drawn the same way, with its own
border tiles in `assets/tiles/shroud.png`.

## Camera and minimap

- `MapCamera` (`scripts/ui/map_camera.gd`) scrolls with the arrow keys and when
  the mouse touches a screen edge, at 480 pixels (15 cells) per second, and
  stops at the map border. It always sits on whole pixels.
- The map is shown in the left 748 pixels of the 960-pixel-wide screen; the
  right 212 pixels are the sidebar.
- `Minimap` (`scripts/ui/minimap.gd`) draws one coloured pixel per cell, scaled
  up, with a frame showing what the camera sees. Clicking or dragging on it
  moves the camera.
- The minimap shows unexplored cells in black, units as coloured dots and,
  in a mission, the control area as a ring.
- When nothing is selected the sidebar shows the cell under the mouse: its
  position, terrain and whether it can be crossed or built on. This is a
  development aid, not final HUD.
